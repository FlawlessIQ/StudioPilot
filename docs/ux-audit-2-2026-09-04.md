### N2 addendum — one session per browser: opening the couple invite signs the studio out
- Clicking "Sign in with another account" on the couple invite performed a global Firebase sign-out for the profile. The studio tab immediately dropped to `/auth/login` (session gone). So in a single browser a solo operator cannot preview the couple's invite/portal without losing their studio session, and getting back in requires the studio password again. Reinforces P19 and argues for either a tokened read-only guest view that doesn't disturb the studio session, or multi-session support.

### N2 correction — the broken branch is "already signed in as another account"

So the token IS honored; the couple simply must create a password account (P19: no passwordless option, but not broken).

### N5 (new, medium — P20/P21 family) — vestigial approvalState strands a checkpoint and mis-attributes a couple action
- Published schedule carries `approvalState: "client_pending"`, but there is no couple approval mechanism (P20 removed the button). So the readiness checkpoint "Final run of show approved · completes when the couple approves" can never complete via the couple — only a studio waive clears it.

P20's fix was cosmetic (email copy + button removal); the underlying vestigial approval flow still produces a stuck checkpoint and a misleading couple next-action. Recommend fully retiring `approvalState` (auto-approve on publish, or make the checkpoint studio-owned) rather than leaving it `client_pending`.

### N6 (new, medium) — "Record and release delivery" silently no-ops when the review-destination URL is blank
- With all visible fields valid and the button enabled, clicking "Record and release delivery" (real click and programmatic submit) fired **no request, no console error, no state change** — the studio is stuck with zero feedback.
- Cause (DOM inspection): in the collapsed "Follow-ups and studio defaults" section, `reviewDestinationLabel` defaults to "google" but `reviewDestinationUrl` is **required and empty**, so react-hook-form blocks submit — but the error is inside a collapsed section and nothing surfaces at the button. Fix: surface the validation error (and/or expand the section on failed submit), or don't require the review URL at release, or don't preset a review label without a URL.

### Final invoice (P-tail) — not reachable on a past-dated project
- `/studio/invoices` still says "No final invoice is due… starts 28 days before an eligible event" even post-event. The final-invoice review window is **pre-event only** ([event−28d, event]); a past event has exited it. Combined with there being no reschedule control, a single fixture can't reach both the final QB invoice (needs a future event within 28 days) and the post-event tail (needs a past event). The live QB final-invoice test (Conor's request) therefore needs a *future-dated* fixture (event within 28 days) — noted as outstanding rather than forcing yet another project this pass.

### Closeout — blocked on the final balance (coherent gate)
- "Reconcile evidence" result: outstanding = **Final QuickBooks balance not settled**; passed = final schedule published, gallery delivered & accessed, review request sent. Delivery record: Marlow & Reese · pixieset · Delivered Sep 5 · Expires Dec 4 · sent.
- CLOSED requires the final balance settled; the closeout assistant surfaces only "Reconcile evidence" (no attest-to-close for the balance here). Because the final invoice is unreachable for a past-dated event (window is pre-event), CLOSED can't be reached on this fixture. This is a correct gate, not a defect — a real project would have invoiced/collected the balance in the pre-event window.
