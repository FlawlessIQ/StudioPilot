# UAT walk — 2026-09-22

A fresh comped tenant (`conor+uat@flawlessiq.com`, "Test"), walked on
production through Chrome. Scope: everything shipped since 2026-09-21, the
client portal, and — asked for explicitly — that **videographers can be added
as crew and to packages**.

Six defects found. All six fixed and shipped, each with a guard confirmed
failing on the original.

---

`includedPhotographers: 0`. The pre-fix `Coverage 480` / bare `Yes` is gone and
the status pill is labelled.

**Videographers as crew.** Three profiles, trades read back from Firestore

| Marco Silva | `["videographer"]` |
|---|---|
| Jordan Reid | `["photographer"]` |

Created with the exact sequence that produced `trades: []` in the 09-20 audit —

Then offered for real: the videographer role went to **Marco Silva**, second
photographer to Alex Rivera, both emails `succeeded` and `branded: true`.
Jordan was correctly never offered the videographer role.

## What the walk found

1. **The register page promised "No card required"** and named a deleted plan.
   False since billing enforcement (09-07); the next screen asks for a card.
2. **The staffing list showed an order the offers did not use.** A
   photographer-only profile displayed as "2" for a videographer role, and the
   reorder arrows never reached the plan — moving a preferred videographer to
   the top changed the list and nothing else.
3. **Cue could never select a package** — its picker omitted the required
   `discount`, so every attempt returned `400 INVALID_COMMAND:discount`.
4. **…and said so in machine code**, via `caught.message.replaceAll("_"," ")`.
5. **Cue dropped every crew flow.** `resolveFlowProjectId` required the whole
   stored project name in the sentence; jobs are filed "<couple> Wedding" and
   operators type the couple. See `fixtures-must-match-real-names`.
6. **The crew picker opened on a hardcoded "Second photographer"**, so asking
   for a videographer ranked the roster for photography and listed the only
   videographer last as "Role or specialty does not match".

Findings 5 and 6 were sequential: fixing 5 made the flow render, which exposed
6 immediately.

## The purge, walked end to end

Refused on the live job — *"Someone is still waiting on this job"* — enforced
server-side as `PROJECT_HAS_LIVE_CREW`, not merely in the UI. Tested instead on
a throwaway job so the live offers survived.

The confirmation is genuinely double: type the exact job name (the button stays
disabled until it matches), then *"Delete … and 3 records now? This cannot be
undone."*

The manifest is **computed, not boilerplate** — it listed 1 audit entry, 1
system event, the job itself, and named the contact whose only job it was. A
Firestore snapshot taken beforehand matched it line for line.

Afterwards: project gone, **zero** records still referencing it (bar the
deliberately protected `projectPurges` receipt), the throwaway contact deleted,
**Erin DeMattia untouched**, and crew/packages/invitations/emails all intact.
The receipt records who, when (4.2s), per-collection counts and contact ids —
so a purge stays auditable after its records are gone.

## The client portal, walked as the client

Signed in as `conor+erin@flawlessiq.com` and walked every page.

**It reads well.** "Hello, Erin.", 270 days to go, and a calm status —
*"Your studio is reviewing your inquiry. No action is needed from you right
now."* The empty states say what will appear rather than that nothing is there:
payments promises "the amount, the due date and a secure way to pay". At 400px
there is no horizontal overflow anywhere and the bottom tab bar carries the nav.

**Nothing leaks.** Checked the rendered portal for crew names, rates, W-9 and
insurance state, other clients, and package pricing: none present.

**Scoping holds under attack, not just in the UI.** Captured a real
authenticated portal request and replayed it with other project ids:

| Request | Result |
|---|---|
| Her own job | 200 |
| The purged job | 403 `PROJECT_ACCESS_DENIED` |
| A made-up job id | 403 |
| Her own job id under a **different tenant** | 403 |

**One defect, fixed.** A message the couple had just written rendered
`You · September 22, 2026 · Received`. Status is stored from the studio's side
(`direction: inbound, status: received`), and the thread rendered it verbatim
for both sides — while the confirmation a second earlier had said "Message sent
securely to your studio." The line already knew `fromStudio`; only the status
ignored it. The couple's own messages now read "Sent".

The client→studio path itself works: the message stored as inbound and the
studio was notified.
